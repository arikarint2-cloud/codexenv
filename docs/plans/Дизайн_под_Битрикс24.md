# Привести лендинг к дизайн-системе Bitrix24 UI Library

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

If this repository contains `.agent/PLANS.md`, this plan must follow it.

## Purpose / Big Picture

Переодеть существующий лендинг в визуальный язык дизайн-системы из Figma (`Bitrix24 UI Library - MVP v.0.5`), сохранив текущую структуру секций, контент и интерактив. После выполнения пользователь получит страницу, которая выглядит и ощущается как часть единого продуктового стека Bitrix24, а не как изолированный кастомный экран.

Ключевой результат:
- токены (цвета, типографика, радиусы, тени, отступы) синхронизированы с дизайн-системой;
- компоненты лендинга (header, кнопки, карточки, FAQ, поля формы) приведены к паттернам DS;
- функциональность (`script.js`) и пользовательские сценарии не ломаются.

## Surprises & Discoveries

- Observation: Проект реализован как статический лендинг без сборщика и без framework-слоя.
  Evidence: В корне присутствуют `index.html`, `styles.css`, `script.js`; отсутствуют `package.json` и build-config.

- Observation: В проекте уже есть утверждённый визуальный слой и рабочая интерактивность (мобильное меню, FAQ, валидация формы).
  Evidence: `styles.css` содержит текущую систему токенов `:root`; `script.js` реализует навигацию и submit-валидацию.

- Observation: Существующий план по лендингу уже задокументирован в `docs/plans/Экспертный_лендинг.md`.
  Evidence: Файл присутствует и отражает выполненные этапы разработки и тестов.

- Observation: `get_design_context` и `get_variable_defs` для указанной Figma-ноды возвращали ошибку про отсутствие выбранного слоя, несмотря на переданные `fileKey/nodeId`.
  Evidence: MCP ответы с `INVALID_ARGUMENT` и текстом `You currently have nothing selected`.

- Observation: `get_metadata` для ноды `3382:12064` вернул информационный холст (гайд по разделам DS) без прямой выгрузки численных токенов в ответе.
  Evidence: В XML-метаданных отражены разделы `Colors`, `Typography`, `Shadow`, `Space`, `Border`, но не итоговая таблица конкретных значений.

- Observation: Автоматическая проверка через Playwright MCP не смогла открыть локальный `file://` URL новой страницы.
  Evidence: Ошибка `Access to "file:" protocol is blocked` при навигации на `tea-break.html`.

## Decision Log

- Decision: Не менять архитектуру проекта (HTML/CSS/JS), а выполнить миграцию только визуального слоя и стилей компонентов.
  Rationale: Задача сфокусирована на «переодевании» под DS, а не на техническом рефакторинге.
  Date/Author: 2026-05-08 / Codex

- Decision: Использовать Figma как единственный источник истины для токенов и компонентных параметров, с явной маппинг-таблицей в CSS.
  Rationale: Это уменьшает субъективные решения и упрощает последующие правки по системе.
  Date/Author: 2026-05-08 / Codex

- Decision: Сохранять текущую DOM-структуру секций по максимуму; добавлять новые class/utility-обёртки только при необходимости соответствия DS.
  Rationale: Минимизирует риск регрессий в контенте, якорной навигации и JS-сценариях.
  Date/Author: 2026-05-08 / Codex

- Decision: Выполнить DS-миграцию через системный продуктовый стиль Bitrix24 (Segoe UI + корпоративная blue-палитра) с маппингом на существующие CSS-переменные.
  Rationale: Прямой экспорт численных токенов из выбранной ноды оказался недоступен, но в DS-гайде явно зафиксированы направления (типографика system/Segoe UI, color/bg/shadow/space).
  Date/Author: 2026-05-08 / Codex

- Decision: Новую страницу по референсу собрать как отдельный статический файл `tea-break.html` и отдельный стилевой модуль `tea-break.css`, без изменений меню/роутинга существующих страниц.
  Rationale: Пользователь явно попросил добавить страницу отдельно и не добавлять пункт в меню; изоляция стилей исключает регрессии текущего лендинга.
  Date/Author: 2026-05-12 / Codex

## Context and Orientation

Текущее состояние репозитория:
- `index.html`: вся структура лендинга (hero, services, process, cases, pricing, faq, lead form).
- `styles.css`: текущие кастомные токены и компоненты UI.
- `script.js`: интерактив (мобильное меню, FAQ, валидация формы).
- `assets/favicon.svg`, `assets/og-cover.svg`: базовые публикационные артефакты.

Целевой источник дизайн-системы:
- Figma: `https://www.figma.com/design/zA1UGS07qtUVd7XSexyw0t/Bitrix24-UI-Library---MVP-v.0.5?node-id=3382-12064&t=ComlmpWODjlxeMbS-1`

Ожидаемые области миграции:
- Дизайн-токены (`:root` в `styles.css`): цвета, типографика, spacing scale, border radius, shadows.
- Компонентные стили: `.site-header`, `.main-nav`, `.btn*`, `.card`, `.faq-list details`, `input/textarea`, состояния hover/focus/active.
- Респонсив-поведение: брейкпоинты и отступы должны быть согласованы с DS-гайдом (если определён).

## Validation and Acceptance

Валидация должна подтвердить два класса критериев.

1) Функциональные (регрессий нет):
- меню открывается/закрывается на mobile;
- якорные ссылки ведут к корректным секциям;
- FAQ раскрывается/сворачивается;
- форма показывает корректные ошибки и успех при валидном вводе.

2) Визуальные (DS-соответствие):
- цвета, типографика, отступы, радиусы и тени соответствуют выбранной DS-конфигурации;
- кнопки, карточки и инпуты выглядят как системные компоненты, а не кастомные исключения;
- desktop/mobile версия визуально консистентны.

Acceptance (observable behavior):
- пользователь открывает лендинг и видит интерфейс в стиле Bitrix24 UI Library;
- ключевые интерактивные сценарии работают так же, как до «переодевания».

## Idempotence and Recovery

- Изменения будут в основном в `styles.css`, поэтому повторная правка безопасна при пошаговой проверке.
- Если отдельный компонент уходит от DS или ломает UX, откат выполняется локально по компонентному блоку (header/button/form), без массовых удалений.
- Перед крупными перестройками стилей использовать маленькие инкременты и промежуточные проверки в браузере.
